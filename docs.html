Design Documentation

How This Was Built

This page explains the design choices, the code structure, and the user-experience ideas behind the project. Sections 01–07 walk through the project area by area; section 08 (Design Decisions — Quick Q&A Reference) collects the most likely questions in a single index, each answer pointing back to the relevant section.

01

Concept & Information Architecture

The main goal was to avoid two common problems: a film database (full of facts, but boring), and a tourist guide (easy to use, but too shallow). The solution was to add a narrative layer on top of the location data. The same locations are shown in two different journeys.

With this structure, one location can have different text, different order, and a different mood — depending on which narrative the user picks. The project does not duplicate pages. Instead, one data model holds different texts for each narrative.

The site has six pages: Cover (start page), Map, Explore (the main experience), About, Documentation, and Disclaimer. The pages are linked in a clear order. The Explore page is the most interactive one and works almost like a small app.

Data Model

All content is stored in one file: data.js. The data is kept separate from the design. This way the same data can drive every page, and switching between narratives is instant.

State Management

The app remembers what you are doing — which narrative is active and which location you are reading — using localStorage. So if you change pages, you do not lose your place.

02

UX Design Principles

The design shows one location at a time, with enough space for the text. We did not want to show everything at once. The user moves through the locations in order, like chapters in a book or scenes in a film.

The site supports three ways to use it:

  • Planning at home: Pick a narrative on the Cover page, check the Map to see where the locations are, then go through the Explore page in order. Arrow keys also work.
  • On-site visit: Use the Map to find the nearest location, then open the Explore page for the text. The chapter strip lets you jump between sections quickly.
  • Reading at the desk: The About and Documentation pages show the project's background. Each location also has a "Narrative Note" — a short analytical comment.

Navigation Patterns

Previous and Next buttons move the user one step at a time. Dots show all locations at once. The chapter strip jumps between sections. Arrow keys (← →) also work on the Explore page.

Progressive Disclosure

Information is shown step by step: film tag and location name first, then the scene, then the quote, then the full text, and finally the narrative note. The user can stop reading at any level.

Responsive Layout

On a desktop, the Explore page has two columns (image left, text right). On a phone, the columns stack vertically. The Map sidebar also adapts to small screens. Buttons are big enough to tap.

Narrative Transition

When the user changes narrative, the text fades out and back in over 350 ms. This is fast enough to feel quick but slow enough to show that the content has changed.

03

Visual Design System & Themes

Following the LMML brief, this individual project ships two switchable themes. The two themes are not just different fonts and colours: they differ in font family, palette, background imagery, layout, ordering and overall look & feel — so the same content reads as two visually different exhibitions. One theme reflects the qualities of the late-XX / XXI-century screen; the other reflects XIX-century / mid-XX-century print.

Both themes share one design system. Tokens (colours, fonts, spacing) live as CSS custom properties on :root; the Heritage theme overrides them through a [data-theme="heritage"] selector. The active theme is chosen with the round button pair in the navigation bar (◉ / ❦) and persisted in localStorage, so the choice survives across pages and reloads.

Theme A — Cinematic (XXI-century screen)

Why this theme exists. The Pursuit & Passage narrative and the 2012 / 2014 / 2016 chapters of the Through Time narrative are dominated by post-2010 digital cinema — Skyfall, Taken 2, The Water Diviner, Inferno. These films share a darker palette, anamorphic framing, and a kinetic, on-screen feel. The Cinematic theme matches that register: a dark "projection room" background, strong contrast typography, and an asymmetric left-anchored hero that imitates a widescreen title card.

Background image. A pure-CSS pattern on body::before: two thin filmstrip-perforation columns on the left and right edges, plus a soft radial vignette, evoking an unreeled 35mm strip and the screen falloff of a dark cinema.

Theme B — Heritage (XIX-century print & 1960s academic press)

Why this theme exists. The 1960s chapter of the Through Time narrative — From Russia with Love (1963), and the "tourist Istanbul" gaze it established — belongs to a slower, documentary, mid-century European cinema. Reading those locations on a black "spy" background flattens that history. The Heritage theme places them on parchment, in a transitional serif, with a centred, book-style measure. It is also the better register for scholarly long-form reading: the doc, about and disclaimer pages gain a drop-cap and ornamental section breaks.

Background image. A pure-CSS pattern on body::before: three soft sienna/oxblood radial washes laid over a faint diagonal weave, evoking ebru (Turkish marbled paper) endpapers — a deliberate Ottoman/Levantine geographic anchor that ties the typographic tradition to the project's actual subject city.

What both themes must handle

The LMML brief states that any theme must remain useful for many different exhibitions, not just the one it was designed for. Both themes here pass the same three capability tests, so the same data file could power a different cinema-tourism project tomorrow without redesign:

  • Multiple texts of various lengths. Each location carries three text variants (young / adult / scholar), a short quote and a separate narrative note. Both themes set sensible measure (≈ 60–75 characters per line) so a 40-word quote and a 300-word scholar essay both look intentional.
  • Images and captions. Each location has a tabbed gallery (real location vs. film still) with multiple thumbnails and a per-image caption. Both themes style the gallery, captions and the floating film tag with theme-appropriate borders, fonts and colours.
  • Reasonably sized metadata tables. The Details panel renders the full LOC_META record as a five-section table (Location / Heritage / Scene / Tourism / Project). Both themes restyle the section headings, the vocabulary tags and the row borders without changing the table's structure.

04

Technical Architecture

The project is a simple multi-page static website. It uses plain HTML, CSS, and JavaScript only. There are no build tools, no frameworks, and no server. The site can run from any folder or any basic web host. The code is easy to read and easy to share — which fits the course goals.

Dependencies

No npm, no bundler, no framework.

Semantic HTML

All pages use the right HTML5 tags: <nav>, <main>, <section>, <article>, <header>, <footer>, <blockquote>. ARIA attributes describe the interactive parts for screen readers.

CSS Architecture

One stylesheet, with clear comments for each section. Colours and sizes are stored as CSS variables in the :root selector. The layout is mobile-first. No preprocessor (like Sass) is needed.

05

Content Strategy

Each location has four content layers. Each layer answers a different need:

  • Quote — one short italic sentence. It sets the mood before the user reads the full text. Short enough to read quickly.
  • Narrative Description — 100–150 words. Describes the scene as it happens in the film. Written in present tense. Mentions specific film moments and exact places.
  • Narrative Note — 60–100 words. A short comment that steps outside the film. It adds historical, geographic, or cinematic context for readers who want more.
  • Film Tag & Coordinates — facts that are always visible on the image panel. The GPS numbers connect the text to the real place, useful when you visit it.

06

Metadata Model

Every location has a metadata record. The same record is shown in two ways: as a visible table in the Details panel of the Explore page, and as a JSON-LD block in the page <head> for search engines and other tools. Both come from the same place in the code: the LOC_META object in js/data.js.

The records are grouped into five sections: Location, Heritage, Scene, Tourism, and Project. Each section answers a different question about the place. The sections use a small mix of standard vocabularies, because no single standard covers everything (geography, old buildings, film scenes, tourism, and editorial credits).

How the model is Rich, Systematic, Tailored, Uniform

Rich

Each record has many fields: address, Wikidata ID, year built, architects, style, UNESCO status, visit duration, accessibility notes, sources. No record has only coordinates.

Systematic

All 16 locations use the same 5 sections. If a field is missing for one place, the field stays empty — it is not silently removed. So the same shape is visible for every location.

Tailored

The model holds two kinds of facts: heritage facts (year built, architect) and cinema facts (camera angle, film role). They live side by side, without one being forced to look like the other.

Uniform

The HTML table and the JSON-LD are built from the same LOC_META object. So a human eye, a screen reader and a search engine all see the same record.

Where the machine-readable metadata lives

The machine-readable metadata is written as <script type="application/ld+json"> blocks directly inside the <head> of each HTML file. No JavaScript is needed. You can right-click any page, choose "View page source" (or press Ctrl+U), and you will see the JSON-LD as plain text in the source.

Each page also has Dublin Core <meta> tags (DC.title, DC.creator, DC.date…) and Open Graph tags for social-media sharing. Together these three layers (Dublin Core meta, Open Graph meta, JSON-LD) cover every common metadata reader.

Each page uses the Schema.org type that fits its role:

  • index.html — WebSite + CreativeWork (cover page).
  • map.html — Dataset (a list of 16 locations).
  • explore.html — CollectionPage with hasPart[] containing all 16 locations as Schema.org Places. Every location is fully described in one static block.
  • about.html — AboutPage.
  • docs.html — TechArticle (this page).
  • disclaimer.html — WebPage (with specialty: "disclaimer").

You can check the output in two free tools: the Schema.org validator and Google's Rich Results Test. Both tools work with the static HTML — no need to run JavaScript.

Vocabularies used and why

  • Schema.org — the main type system. Every location is a schema:Place (or LandmarksOrHistoricalBuildings if it has a year built). Address, coordinates, film, tourism fields all map to standard Schema.org types. Chosen because Google, Bing and accessibility tools read it directly.
  • Dublin Core (dcterms:*) — for the editorial facts: source, rights, last updated, language. Chosen because it is the common standard in libraries and archives.
  • Wikidata Q-IDs — each location has a Wikidata ID, like Hagia Sophia = Q12506. The ID is clickable in the table and also exported in the JSON-LD. Chosen because it is a single global ID that any other system can use to find the same place.
  • GeoNames IDs — for the city / country level. Chosen because it gives a stable code for the whole region.
  • Project namespace (lmml:*) — for the cinema fields that Schema.org has no clean name for: camera facing, focal length, shot type, film role. Used only when no good standard term exists.

07

Accessibility Considerations

The site aims to follow WCAG 2.1 Level AA. Main points:

  • ARIA labels on every button and important region, so screen readers can describe them.
  • Keyboard navigation — the Explore page works with the keyboard only. Arrow keys move between locations.
  • Colour contrast — main text on the dark background has a contrast ratio above 4.5 : 1. Lighter grey is only used for small extra info.
  • Live regions — when the narrative changes, screen readers are told politely (aria-live="polite"), without interrupting the user.
  • Semantic structure — every page uses heading levels in the right order (h1 → h2 → h3).

08

Design Decisions — Quick Q&A Reference

Every design choice on this site is documented in the sections above. This final section collects the most likely questions in one place. Each answer points to the section that explains it in full.

8.1 Typography

Q. Why two typefaces per theme — a serif and a sans-serif?

A. A serif gives identity (display, quotes); a sans gives legibility at small sizes (UI, captions). This is the standard "bicameral" pairing in editorial typography. See § 3 Visual Design System.

Q. Why Playfair Display for the Cinematic theme?

A. Playfair is a high-contrast Didone serif — the same family used on contemporary movie posters and on modern film title cards. It signals "cinema" instantly. Pairs with Inter for screen-optimised body text. See § 3.

Q. Why Cormorant + EB Garamond for the Heritage theme?

A. Both are open-source revivals of Claude Garamond's 1592 punches. EB Garamond is tuned for long reading (used by Harvard UP, Princeton UP and other scholarly presses); Cormorant is its display counterpart. Together they evoke the 1950s–60s European academic press — which matches the 1960s chapter of the Through Time narrative. See § 3.

Q. Why JetBrains Mono for coordinates?

A. A monospaced face makes numerical/technical data (GPS, focal lengths, years) align in vertical columns and read as "data" at a glance, distinct from prose. See § 3.

Q. Why clamp(2rem, 5vw, 3.5rem) for h1?

A. clamp(min, preferred, max) lets the heading scale fluidly with the viewport (5vw) but never collapses below 2 rem on phones nor explodes above 3.5 rem on large screens. No media-query breakpoints needed for type. See § 4 Technical Architecture.

Q. Why a base font size of 16 px?

A. 16 px is the browser default and the W3C-recommended baseline. Every rem value in the stylesheet is a multiple of this single anchor, so a user who raises their browser default automatically gets a larger UI.

Q. Why line-height: 1.75 for body text?

A. 1.5–1.8 is the typographic comfort range for body prose (Bringhurst, The Elements of Typographic Style). 1.75 lands in that range and matches the slightly looser leading of mid-century European book design — which the Heritage theme is built around.

Q. Why uppercase + extra letter-spacing on labels and buttons?

A. Uppercase needs ~0.08 em–0.18 em of letter-spacing to stay readable; this pairing is the standard for small-caps labels and mirrors the running heads of mid-XX century academic editions.

8.2 Colour

Q. Why these specific hex values for gold (#c9a55a) and steel-blue (#4a8bb5)?

A. The two narrative dots had to be (a) clearly distinct for colour-blind viewers and (b) anchored to film-stock atmosphere. Gold #c9a55a evokes the warm halation of tungsten-lit interiors; blue #4a8bb5 evokes the cool steel of espionage cinematography. Each token is named for its function (--accent-gold, --accent-blue), not its hex — so the Heritage theme redefines them to sienna and prussian blue without renaming. See § 3.2 Cinematic palette.

Q. Why a dark Cinematic palette and a light Heritage palette?

A. Two reasons: (1) Cinematic imitates a darkened cinema/projection room; Heritage imitates a printed book on archival paper. (2) Light versus dark is the most legible difference between two themes at first glance — and the brief explicitly asks the themes to differ on more than colour alone. See § 3.

Q. Why CSS custom properties for colour?

A. Themes are switched by setting data-theme="heritage" on <html>; the variables redefined under that selector cascade everywhere automatically. No JavaScript walks the DOM to repaint. Implemented in css/style.css § 28.

Q. Are the colour pairings WCAG AA compliant?

A. Body text on the dark background passes WCAG AA (≈ 13 : 1 contrast; required: 4.5 : 1). Muted text is reserved for non-essential labels (timestamps, vocabulary tags) where AA Large Text (3 : 1) is sufficient. See § 7.

8.3 Spacing & Layout

Q. Why a six-step spacing scale (4 → 96 px)?

A. A geometric progression (--space-xs 4 px → --space-3xl 96 px) prevents the "random margin" problem: every gap on the site comes from one of seven values. Vertical rhythm stays consistent automatically. Defined in css/style.css:50.

Q. Why a navigation bar exactly 60 px tall?

A. 60 px is large enough for the brand mark and ≥ 44 × 44 pt tap targets on mobile (Apple HIG), but small enough that the cover-page hero still dominates above the fold on a 1080 p laptop. Token: --nav-height.

Q. Why image-left / narrative-right on the Explore page (Cinematic)?

A. Cinema is a visual medium — the still leads the eye, the text supports it. Mirrors the convention in printed art books (image on recto, caption on verso). Heritage flips the order to echo a book where text introduces the figure plate. See § 3.3 Heritage layout.

Q. Why is the cover hero left-anchored in Cinematic but centred in Heritage?

A. Asymmetric left-anchored layout dominates 21st-century cinema and streaming UIs (Netflix, Criterion Channel). Centred title-pages dominate XIX-century print and Tschichold's 1950s Penguin redesigns. The two heroes inherit from two different historical typographic moments. See § 3.

Q. Why clamp() instead of media-query breakpoints for type?

A. clamp(min, preferred, max) produces a smooth curve between phone and desktop, with no jump at the breakpoint. Saves dozens of lines of media-query overrides for typography.

Q. Why a single style.css file (not multiple modules)?

A. Browsers cache one file better than many. The file has a 29-section table of contents at the top so a reader can jump to any section in seconds. Splitting would require a build step, which the brief deliberately avoids.

8.4 Two Themes

Q. Why two themes at all?

A. The brief asks for two themes that differ on colours, fonts, layout, ordering, and look-and-feel — not just colour. Each theme also serves a different reader: Cinematic for casual browsers of the post-2010 pursuit narrative; Heritage for scholars / heritage readers of the 1960s timeline. See § 3.

Q. What exactly differs between the two themes?

A. Five axes: (1) Colours (dark amber/blue → light sienna/prussian); (2) Fonts (Playfair + Inter + JetBrains Mono → Cormorant + EB Garamond + Alegreya Sans SC); (3) Layout (image-left → image-right, mirrored); (4) Ordering (image → gallery → info → info → image → gallery in the visual column); (5) Look-and-feel (filmstrip background, sharp shadows → ebru washes, double-rule borders, drop-cap on first paragraph).

Q. How is the theme persisted across pages?

A. localStorage.theme is read by an early IIFE at the bottom of app.js and written to <html data-theme="…"> before the first paint, so there is no flash of unthemed content. See js/app.js.

8.5 JavaScript Architecture

Q. Why no framework (no React, no Vue)?

A. The site has six static pages and one stateful page (Explore). A framework would add ~150 KB of runtime to deliver functionality that ~600 lines of vanilla JS already provide. The simpler architecture is also more defensible for a beginner-level course. See § 4.

Q. Why a single App module (revealing-module pattern)?

A. One global namespace (window.App) groups all state and helpers; nothing else pollutes the global scope. Beginner-readable: one place for state, one place for helpers, one place that decides what is public. See js/app.js.

Q. Why localStorage for state instead of URL parameters?

A. localStorage survives page navigation and reload, matching user expectation: "I was on location 4; when I come back I want to be on location 4 again." URL parameters (?n=pursuit&loc=galata-tower) were added on top for shareable deep links.

Q. Why CustomEvents (narrativeChanged, locationChanged) instead of direct calls?

A. Each page binds its own listeners. The Explore page redraws on locationChanged; the nav badge updates on narrativeChanged. Decoupling state mutations from UI updates means a new page can react to the same events without touching App.setNarrative().

Q. Why three audience levels (Young / Adult / Scholar)?

A. Reading level adapts the same factual content to three audiences: simple-English narrative tone for young visitors; informative tourist tone for general adults; scholarly heritage register for academic readers. This is the "Tailored" leg of RSTU. See § 6.

Q. Why short / medium length on top of the audience axis?

A. Audience is competence × tone; length is independent. A young visitor might want a long friendly text, a scholar might want a short dense text. Two axes × three values give up to 6 versions of each text per location.

Q. Why the Haversine formula for the "walk to next" distance?

A. Haversine gives great-circle distance between two [lat, lon] points on a sphere — exact enough for distances under a few km in a single city. We are not modelling street routing; we are giving the visitor a "how far and which way" hint. See js/explore.js.

8.6 Metadata & Semantics

Q. Why mix Schema.org, Dublin Core and Wikidata instead of one vocabulary?

A. Each vocabulary covers a different facet: Schema.org for places/buildings/coordinates; Dublin Core for editorial provenance (source, rights, date, language); Wikidata for unique global IDs of named entities (Hagia Sophia = Q12506). Each row of the table tags itself with the vocabulary in use, so the model is visible in the UI. See § 6.

Q. Why JSON-LD in the <head> instead of injected by JS?

A. Search engines and accessibility tools index the static HTML. JSON-LD blocks in <head> are visible in View Source without running any JavaScript. JSON-LD is the format Google explicitly recommends. See § 6.

Q. Why five sections in the metadata table?

A. Each section answers one reader question: Location (where), Heritage (what kind of building, when, by whom), Scene (which film, which shot), Tourism (how do I visit), Project (who curated this and when). Same structure on every record → the "Systematic" leg of RSTU. See § 6.

8.7 Accessibility

Q. Why arrow-key navigation between locations?

A. Keyboard navigation is a WCAG 2.1 success criterion (2.1.1). Arrow keys are intuitive for previous/next and don't conflict with browser shortcuts. See § 7.

Q. Why ARIA role="tab" on the dot navigation?

A. The dots are not decorative; each targets a specific location. Marking them as a tablist makes them discoverable to screen readers, with aria-selected announcing the current one.

Q. Why position: sticky on the details-panel close button?

A. The details panel can scroll vertically (max-height: 60vh). Sticky positioning keeps the close button reachable from any scroll position, without forcing the user to scroll back to the top.

Q. Why aria-hidden="true" on glyph icons (◉, ❦)?

A. Glyph icons are decorative — they don't carry meaning beyond what the visible text already says. Hiding them from the screen-reader buffer prevents the same word being announced twice.
